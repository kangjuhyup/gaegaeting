# 인앱결제 간식 충전 모듈 설계

작성일: 2026-10-05. 상태: 사용자 대화에서 iOS·Android 동시 지원 및 구현 진행 승인. 이후 결제·지갑·아이템 내부 모듈 분리 요청을 반영했다. 실행 설정과 검증 방법은 [Payment README](../../../packages/payment/README.md)를 기준으로 한다.

## 확정된 요구사항

- 사용자가 특정 금액을 결제하면 서비스 내 재화인 간식이 충전된다.
- 우선 인앱결제를 지원한다.
- 웹결제는 이후 지원한다. 이번 설계에서 결제 수단과 간식 지급 규칙을 분리한다.
- 간식에는 유효기간이 없다.
- 사용 후 환불은 불가하다. 구매 건의 간식을 일부라도 사용하면 해당 구매 건은 서비스의 환불 대상에서 제외하는 것으로 해석한다.
- 초기 기본 상품은 10개 2,000원, 50개 6,000원, 100개 10,000원이다.
- 추후 이벤트에서 기본 가격보다 저렴하게 판매할 수 있어야 한다.

## 기본 상품과 이벤트 판매

| 상품 | 지급 간식 | 기본 가격 | 통화 |
| --- | --- | --- | --- |
| 간식 10개 | 10개 | 2,000원 | KRW |
| 간식 50개 | 50개 | 6,000원 | KRW |
| 간식 100개 | 100개 | 10,000원 | KRW |

상품의 간식 수량과 판매 조건을 분리한다. 판매 조건에는 기본·이벤트 구분, 판매 가격·통화, 판매 기간, 활성 여부, 스토어 상품 및 필요한 offer 식별자를 둔다. 가격은 정수 최소 통화 단위로 저장한다. 이벤트 가격과 기간은 이벤트 등록 시 정하고 현재 임의의 할인 가격을 생성하지 않는다.

같은 간식 수량에 대해 기본 판매와 이벤트 판매를 연결할 수 있다. 활성 판매 조건을 데이터로 관리해 새 이벤트를 위해 충전 로직을 수정하지 않도록 한다. 서버의 이벤트 등록만으로 스토어 결제 가격이 변경되지는 않는다. 스토어 가격 예약·offer 또는 별도 스토어 상품을 설정하고 실제 구매 가능한 상태를 확인한 뒤 노출한다. Apple은 기간별 인앱 상품 가격 변경을, Google은 일회성 상품 할인 offer를 지원한다. [Apple 가격 예약](https://developer.apple.com/help/app-store-connect/manage-in-app-purchases/schedule-price-changes-for-in-app-purchases), [Google 일회성 상품 offer](https://developer.android.com/google/play/billing/one-time-product-multi-purchase-options-offers).

이번 확장 범위는 기간별 할인 판매까지다. 쿠폰·사용자별 할인·첫 구매 혜택을 위한 범용 프로모션 규칙 엔진은 별도 요구사항이 있을 때 설계한다.

구매 준비 내역에는 상품 수량, 판매 조건 버전, 이벤트 식별자, 스토어 상품·offer 식별자 및 제시 가격을 저장한다. 검증된 거래의 실제 금액·통화는 별도로 저장하며 제시 가격을 실제 결제액으로 간주하지 않는다. 기본 가격과 다른 검증된 이벤트 결제를 오류로 거절하지 않는다. 이벤트 종료 후에도 이미 결제된 거래는 원래 판매 조건으로 처리한다. 종료 후 새 구매 준비 요청에는 이벤트 조건을 제공하지 않는다.

## 현재 저장소

- NestJS 애플리케이션인 `packages/account`, `packages/match`를 `packages/gateway`의 Apollo Federation으로 연결한다.
- 도메인·application·infrastructure 계층과 CQRS 패턴을 사용한다.
- PostgreSQL 및 MikroORM을 사용하며, ORM 중립적인 트랜잭션 경계는 `packages/core/database/src/transaction/transaction-boundary.ts`에 있다.
- 현재 결제 상품, 결제 내역, 간식 잔액 및 변동 이력 구현은 없다.
- Gateway가 인증된 사용자에게 연결된 서비스 사용자 ID를 제공한다. 결제 소유자는 이 ID를 사용한다.
- 모바일 앱은 별도 저장소에서 관리한다. 이 저장소에서 앱의 스토어 구매 화면을 구현할 수는 없다. [인증 연동 계약](../../central-auth-client-integration.md)을 참고한다.

## 구현에서 채택한 운영 규칙

- iOS와 Android 모두 지원한다.
- 구매 시간 기준 FIFO로 사용하고 구매 건별 사용 이력을 유지한다.
- 사용 후 스토어 확정 환불은 남은 간식을 회수하고 원래 사용한 수량을 기록한다. 지갑을 검토 대상으로 보류하며 자동 음수 잔액·다른 구매 건 차감은 하지 않는다.
- 검증된 환불 취소는 해당 환불 회차의 회수 수량만 복원한다. 사용 이력은 유지한다.
- 관리자 상품 편집 화면, 모바일 구매 화면, 실제 운영·스토어 등록은 별도 연동 작업이다.

## 구현 경계

새 `packages/payment` 서비스가 결제 내역과 간식 지갑을 함께 소유한다. Account는 사용자 정보를, Match는 매칭 기능을 계속 소유한다. 간식 잔액을 Account 프로필의 단일 필드로 추가하는 대신 지급·회수 이력과 함께 관리한다.

Payment 안에 `src/payment`, `src/wallet`, `src/item`의 독립 Nest 모듈·서비스·저장소를 둔다. 결제는 각 모듈의 지급 연산을 같은 PostgreSQL 트랜잭션으로 연결한다. 서비스 내부의 SQL 어댑터를 사용해 shared core에 결제 전용 엔티티를 추가하지 않는다.

Payment 안에서 다음 책임을 분리한다.

- 상품: 간식 묶음과 스토어별 상품 ID 연결.
- 결제: 구매자 연결, 스토어 검증, 거래 상태 및 후속 처리.
- 간식 지갑: 충전·회수 원장과 사용자별 잔액.

Apple·Google의 SDK와 API 타입은 infrastructure 어댑터 내부에 둔다. 검증 결과를 서비스 내부의 거래 정보로 변환한 뒤 공통 지급 유스케이스를 호출한다. 향후 웹 PG도 이 흐름을 사용하되 주문 생성·승인·웹훅 검증은 해당 어댑터가 맡는다. 이번에는 웹 PG 구현을 추가하지 않는다.

결제와 지갑을 별도 서비스로 나누지 않아 충전 완료 저장, 원장 생성, 잔액 갱신을 하나의 DB 트랜잭션으로 처리할 수 있다. 사용 후 환불 불가 판정을 위해 지갑에는 구매 건별 사용량을 기록할 경계를 포함한다. 이후 Match 등에서 간식을 쓰는 구체적인 기능과 서비스 간 일관성 계약은 별도 작업이다.

## 상품 및 구매 흐름

간식 충전은 반복 구매 가능한 소모성 상품으로 구성한다. Apple은 소모성 인앱 상품을 제공하며, Google은 소모성 상품 지급 후 consume 처리로 재구매를 허용한다. [Apple 인앱결제](https://developer.apple.com/in-app-purchase/), [Google 일회성 구매 흐름](https://developer.android.com/google/play/billing/lifecycle/one-time).

1. 로그인한 사용자가 판매 가능한 간식 상품 목록을 조회한다.
2. 앱은 스토어 상품 정보를 조회해 실제 결제 가격과 통화를 표시한다. 서버 상품의 참고 가격이나 클라이언트가 보낸 금액으로 스토어 결제를 검증하지 않는다.
3. 서버가 구매 준비 내역을 생성하고 사용자·상품·판매 조건·지급 수량 스냅샷을 저장한다. 앱에는 구매자 연결 값과 스토어 상품 ID 및 필요한 offer 식별자를 반환한다.
4. 앱이 스토어 구매를 진행한다. Apple의 `appAccountToken`, Google의 `obfuscatedAccountId`에 서버가 발급한 구매자 연결 값을 전달한다.
5. 앱이 거래 증거를 서버에 제출한다. 서버는 실제 앱 식별자·환경·상품·구매 상태·구매자 연결 값을 검증한다. 클라이언트가 보낸 사용자 ID나 지급 수량은 사용하지 않는다.
6. 검증이 성공하면 짧은 DB 트랜잭션에서 결제의 지급 완료, 충전 원장, 잔액 변경, 필요한 후속 처리 예약을 함께 저장한다.
7. DB 커밋 후 Google consume을 수행한다. iOS 앱은 서버의 지급 완료 응답을 받은 뒤 거래를 finish한다.
8. 앱은 서버에서 최신 잔액과 충전 결과를 조회한다.

구매자 연결은 서버 사용자 ID와 연결된 Apple용 UUID 및 Google용 불투명 식별자를 사용한다. 스토어가 검증해서 반환한 값이 제출자의 계정 및 구매 준비 내역과 일치해야 한다. 사용자의 계정 전환 후 다른 계정으로 지급하지 않는다. [Apple appAccountToken](https://developer.apple.com/documentation/appstoreservernotifications/appaccounttoken), [Google 구매 검증](https://developer.android.com/google/play/billing/security).

구매 준비 시점의 수량을 유지한다. 동일 스토어 상품 ID의 지급 수량을 변경하지 않고, 다른 수량은 새 상품 버전과 스토어 상품 ID로 판매한다. 판매 중단된 상품도 과거 거래 검증을 위해 매핑을 보존한다.

## 유효기간 및 사용 후 환불

만료일과 자동 소멸 작업을 두지 않는다. 구매한 간식은 사용하거나 환불로 회수될 때까지 유지된다.

환불 여부를 총잔액만으로 판정하지 않는다. 구매 건별 지급·사용·회수 수량과 차감 원장의 배분 내역을 기록한다. 사용 시 오래된 구매 건부터 차감하는 FIFO를 제안하며, 같은 시각이면 고정된 ID 순서로 처리한다. 이 차감 순서를 구현에 적용한다.

- 50개를 구매해 1개를 사용하면 남은 49개만 환불하는 서비스 부분 환불도 허용하지 않는다.
- 이후 10개를 추가 구매해 총잔액이 다시 늘어나도 이전 50개 구매 건의 사용 이력은 유지한다.
- 별도 10개 구매 건이 전혀 사용되지 않았다면 그 구매 건은 사용 여부 조건을 통과한다. 미사용이라는 사실만으로 다른 환불 조건이나 스토어 승인을 보장하지는 않는다.
- 환불과 사용이 동시에 진행될 때는 구매 건을 잠그고 사용 여부를 다시 확인한다. 환불을 진행하는 동안 대상 간식을 예약해 사용과 이중 처리를 방지한다. 외부 환불 요청을 DB 트랜잭션 안에서 실행하지 않는다.
- 구매 건이 미사용이고 환불이 확정되면 해당 건의 간식을 한 번만 회수한다.

서비스의 사용 후 환불 불가 정책을 스토어 환불을 차단할 수 있다는 보장으로 표현하지 않는다. Apple은 사용 정보를 받아 자체 환불 판단에 활용한다. 사용 후에도 스토어가 환불을 확정한 경우 알림을 무시하지 않고 실제 환불 상태를 기록한다. 회수할 잔량을 회수하고 이미 사용한 부족분은 검토 대상으로 남겨 지갑 사용을 보류한다. [Apple 사용 정보와 환불 판단](https://developer.apple.com/videos/play/tech-talks/10887/?time=1133), [Google 무효 구매 처리](https://developer.android.com/google/play/billing/security).

## 정합성 및 복구 제안

- 외부 스토어 호출을 DB 트랜잭션 안에서 수행하지 않는다. 외부 검증 후 저장 시 결제 상태를 다시 확인한다.
- Apple 거래는 제공자·앱·환경·transaction ID, Google 거래는 제공자·앱·purchase token을 기준으로 DB unique 제약을 둔다. Google order ID는 중복 지급 방지 키로 사용하지 않는다.
- 한 거래의 충전 원장에도 unique 제약을 둔다. 앱 재요청과 스토어 알림이 동시에 도착해도 간식은 한 번만 지급한다.
- 사용자 지갑을 잠그거나 원자적으로 갱신해 동시 충전 시 잔액 변경이 유실되지 않도록 한다.
- 결제 대기 상태에서는 간식을 지급하지 않는다. 취소 또는 검증 실패도 지급하지 않는다.
- 네트워크 오류·스토어 일시 장애는 검증 실패로 확정하지 않고 재시도 가능한 상태로 보존한다.
- DB 저장 실패 시 지급 완료를 반환하거나 Google consume을 실행하지 않는다.
- 지급 커밋 후 consume 실패·프로세스 종료는 DB에 저장한 후속 작업으로 재시도한다. 지급 자체를 다시 실행하지 않는다. Google 소모성 상품의 consume은 구매 승인 역할도 한다. 승인 기한은 스토어 계약에 맞춰 관리한다. [Google 일회성 구매 처리](https://developer.android.com/google/play/billing/lifecycle/one-time).
- 앱이 지급 응답을 받기 전에 종료돼도 미완료 거래 재제출 또는 서버 알림을 통해 이어서 처리한다. 구매 준비 내역과 구매자 연결 값이 없는 거래는 임의로 사용자에게 지급하지 않고 조사 대상으로 보존한다.
- 판매 종료·구매 준비 내역 만료만으로 이미 실제 결제된 거래를 버리지 않는다. 보존된 상품 매핑과 사용자 연결을 통해 처리하거나 조사 대상으로 남긴다.

스토어 구매 상태와 서비스 지급 상태를 분리한다. 구매 상태는 대기·구매 완료·취소·환불, 지급 상태는 미지급·지급 완료·회수 처리 대상·회수 완료로 구분한다. 제공자 후속 처리 상태도 별도로 기록한다. 오래된 알림이 이미 환불된 거래를 다시 지급 상태로 되돌리지 않도록 현재 스토어 상태와 원장 이력을 확인한다.

| 구매 준비·거래 내역 | 소유 사용자, 수량·판매 조건 스냅샷, 구매자 연결, 거래 식별자, 구매·지급 상태, 검증 시각, 확인 가능한 실제 결제 금액·통화 |
| 간식 지갑 | 사용자별 한 행, 정수 잔액, 동시 변경 제어 |
| 구매 건별 간식 잔량 | 원본 결제, 지급·사용·회수·예약 수량, 동시 변경 제어, 만료일 없음 |
| 간식 원장 및 사용 배분 | 사용자, 증감량, 사유, 원본 결제, 사용 원장과 구매 건의 수량 연결, 생성 시각, 충전·사용·회수 중복 방지 키 |
| 후속 처리 및 알림 수신 내역 | 작업 종류·거래 연결, 중복 방지 키, 처리 상태, 재시도 시각·횟수 |

원장 내역을 삭제하거나 덮어쓰지 않는다. 회수는 원본 결제와 연결된 반대 방향 원장으로 남긴다. 잔액은 원장 합계 및 구매 건별 잔량 합계와 일치해야 한다. 환불 예약 수량은 보유 잔액에 포함하되 사용 가능 잔액에서는 제외한다. 사용 이력은 이후 충전으로 초기화하지 않는다.

Google token 등 재조회에 필요한 거래 증거는 접근을 제한해 보호하고 로그에 남기지 않는다. 원문이 필요하면 암호화 저장하고 중복 조회용 digest를 별도로 둔다. Apple signed payload는 서명·인증서 체인·앱·환경을 검증한다. 스토어 알림도 제공자별 인증·서명 검증을 통과해야 한다.

## API 및 알림

사용자 GraphQL API는 `snackProducts`, `mySnackWallet`, `mySnackTransactions`, `prepareSnackPurchase`, `confirmSnackPurchase`를 제공한다. 구매 확정 응답에는 결제 ID, 구매·지급 상태, 해당 결제의 지급 수량을 담고 최신 잔액은 별도 조회한다. 다른 사용자의 구매 준비·결제 내역은 접근할 수 없다.

새 서비스는 Gateway에서 payment audience의 내부 assertion을 검증한다. 사용자 API는 `payment:read`, `payment:write` 스코프를 사용한다. 적용하려면 Gateway 정책·Auth 클라이언트·모바일 로그인 요청 스코프가 함께 바뀌어야 한다. 외부 Auth 클라이언트에 결제 스코프를 허용하고 앱에서 요청해야 한다.

서버 알림은 GraphQL 사용자 인증 경로와 별도 HTTP 경로로 받는다. Apple은 Server Notifications V2를 사용한다. Google RTDN은 인증된 Pub/Sub 전달을 검증하고 token으로 스토어 상태를 재조회한다. 알림은 내구성 있게 저장된 후 수신 성공을 응답하고 중복·역순 전달을 처리한다. [Apple 서버 알림](https://developer.apple.com/documentation/appstoreservernotifications), [Google 구매 생명주기](https://developer.android.com/google/play/billing/lifecycle/one-time).

Google 환불은 RTDN만으로 완전하게 감지한다고 가정하지 않고 Voided Purchases API와 대조 작업을 포함한다. Apple은 환불 관련 알림 및 거래 재조회를 사용한다. 미사용 구매 건은 환불 확정 후 회수하고, 사용된 구매 건의 스토어 확정 환불은 구현에서 채택한 운영 규칙에 따라 처리한다. [Google 무효 구매 처리](https://developer.android.com/google/play/billing/security).

## 구현 범위와 순서

1. 정책 및 설계 확정: iOS·Android, 기본 상품, FIFO, 사용 후 스토어 확정 환불의 운영 보류 처리.
2. Backend: Payment 패키지, 데이터 모델·마이그레이션, 기본 상품·판매 조건·지갑·구매 건별 잔량, 구매 준비 및 구매자 연결 구현.
3. Backend: 선택한 스토어 검증 어댑터, 중복 방지·충전 트랜잭션, 후속 처리 복구 구현.
4. Backend: 스토어 알림, 환불 처리, 미완료 거래 대조 구현.
5. Backend·Document: Gateway·인증 계약·로컬 실행·이미지 빌드 설정 연결. 운영 설정은 별도 인프라 저장소와 연동.
6. 별도 모바일 저장소: 스토어 상품 조회, 구매·거래 재제출·완료 처리·잔액 표시 연동.
7. QA: 아래 조건을 실제 PostgreSQL과 스토어 테스트 환경에서 검증.

## 수용 기준

- 검증된 정상 구매 한 건이 해당 상품 스냅샷의 수량만큼 충전된다.
- 같은 거래 재요청, 다른 계정 재제출, 앱과 알림의 동시 처리를 통해 중복·잘못된 사용자 지급이 발생하지 않는다.
- 여러 결제의 동시 지급 후 잔액이 원장 합계와 일치한다.
- 대기·취소·잘못된 앱·상품·환경·서명·구매자 값은 충전하지 않는다.
- 스토어 검증 후 DB 실패, 커밋 후 응답 유실, consume 실패 및 재시도에서 지급 손실·중복이 발생하지 않는다.
- 알림 위조·중복·역순·일시 저장 실패를 처리하고, 환불 누락을 대조 작업으로 발견한다.
- 10개·50개·100개 기본 상품이 각각 2,000원·6,000원·10,000원 판매 조건으로 등록된다.
- 이벤트 판매는 같은 수량을 더 낮은 가격으로 제공할 수 있고, 종료 후 신규 구매에는 기본 판매 조건을 제공한다. 실제 결제 화면 가격은 스토어의 활성 상품·offer와 일치한다.
- 이벤트 결제 재처리 및 이벤트 종료 후 도착한 결제는 당시 판매 조건을 유지한다. 기본 가격과 다르다는 이유만으로 거절하지 않는다.
- 시간이 지나도 사용하지 않은 간식이 소멸하지 않는다.
- 50개 구매 후 1개 사용 시 해당 구매 건의 서비스 환불은 거절된다. 이후 재충전으로 총잔액이 늘어나도 결과가 바뀌지 않는다.
- 미사용 구매 건의 환불 확정 시 대상 간식을 한 번만 회수한다. 사용과 환불의 동시 요청에서 대상 간식을 이중 처리하지 않는다.
- 사용 후 스토어 확정 환불은 실제 환불 내역을 보존한다. 해당 건의 남은 수량만 회수하고 지갑 사용 가능 잔액이 0·보류 상태로 표시된다.
- 소유자만 잔액·거래를 조회하고 운영 환경에 테스트 결제가 지급되지 않는다.
- 상품 판매 중단 또는 수량 변경 이후의 과거 거래 재처리가 원래 수량을 유지한다.
- 선택한 플랫폼의 테스트 구매에서 지급과 거래 완료까지 성공하고 같은 상품을 다시 구매할 수 있다.

구현과 검증은 저장소에 고정된 Node 24.13.1·pnpm 10.34.5 및 별도 PostgreSQL 16.15 테스트 환경에서 수행한다. 최종 검증 결과와 실제 스토어 연동의 남은 조건은 Payment README와 작업 결과에 기록한다.
