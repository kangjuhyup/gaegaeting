# 매칭 기반 채팅 1차 구현

사용자의 채팅 구현 시작 요청에 따라 main과 동일한 파일 트리에서 시작한 `feat/core/chat-messaging`에서 구현한다. DB는 기존 PostgreSQL과 기존 공통 migration/엔티티 계약을 사용하며 Chat 전용 DB `ggt_chat`을 둔다. Match/Account DB를 직접 조회하거나 외래 키로 연결하지 않는다.

## 범위와 계약

사용자의 GraphQL 요구에 따라 Chat은 기존과 동일한 Nest Apollo Federation 2 서브그래프(`/chat/graphql`)로 연결한다. 소비자 UI는 기존 `/gateway/graphql`에서 `chatRooms`, `chatRoom`, `chatMessages` query와 `syncChatRooms`, `sendChatMessage`, `markChatRead` mutation을 사용한다. Match 연동도 내부 assertion으로 인증한 `/match/graphql`의 `chatPairs` query를 사용한다. 저장 어댑터는 pg의 parameterized SQL로 방 잠금/중복/커서를 구현한다.

- 매칭된 두 Account 사용자만 참여하는 1:1 방. `pairId`로 방 생성과 Kafka 재처리를 멱등하게 처리한다.
- Match의 `chat.room.created.v1` 이벤트로 방 생성. 이미 존재하던 매칭과 이벤트 발행 실패는 로그인 사용자의 활성 매칭 조회 후 방 동기화로 복구한다.
- Match 이벤트 발행과 DB 커밋은 서비스 간 원자적이지 않다. 커밋 실패 후 이미 발행된 이벤트로 방이 생성될 수 있으나 전송은 항상 활성 매칭 조회로 차단한다. outbox와 생성 후 정리 정책은 후속 범위다.
- Gateway는 기존 Auth 검증/Account 매핑 후 audience `chat`인 30초 내부 assertion을 새로 발급한다. 클라이언트의 사용자 ID나 내부 헤더를 신뢰하지 않는다.
- 기존 등록된 `match:read`/`match:write` scope를 사용한다. 참여 여부를 모든 방/메시지/읽음 조회와 수정에서 검사한다.
- 텍스트는 공백만 있는 입력을 거절하고 앞뒤 공백 제거 후 1~2000자. 전송 UUID는 `(room, sender, clientMessageId)`로 유일하다. 동일 UUID로 다른 본문을 보내면 409.
- 방 행 잠금 후 메시지를 생성해 같은 방의 커밋 순서와 메시지 ID 순서를 맞춘다. 메시지 저장과 최근 메시지 갱신은 한 트랜잭션이다.
- 메시지는 1~100개(기본 50) 커서 조회. 최신 페이지/과거 `before`/신규 `after` 조회를 제공한다. 읽음은 실제 같은 방의 메시지까지 전진만 가능하다.
- 매칭 취소 후 기존 대화 조회는 유지하고 새 전송은 Match의 활성 상태를 확인해 거절한다. 취소와 전송은 서비스 간 원자적이지 않으며 전송 직전 조회 시점을 기준으로 한다.
- 모바일 채팅 탭을 실제 API에 연결한다. 샘플은 스토리보드와 관심 미리보기에만 유지한다. 송신 성공 시에만 입력을 비우며 실패 후 동일 UUID로 재시도한다.
- 사용자 요구에 따라 GraphQL `chatEvents` subscription을 WebSocket으로 수신한다. Gateway의 WS 경로는 기존 `/gateway/graphql`이며 opaque token을 connection_init에서 검증한다. PostgreSQL LISTEN/NOTIFY는 커밋 이후 변경 신호만 전파하며 실제 데이터는 권한 검사된 query에서 읽는다. 재연결 시 커서로 누락 메시지를 복구하고 반복 polling은 사용하지 않는다. 푸시, 첨부파일, 입력 중 표시, 채팅 삭제와 보존 기간 정책은 다음 구현 범위다.

## 코드 경계

`chat/room`, `chat/participant`, `chat/message` 각각에 domain/application/infrastructure를 둔다. 읽음 상태는 participant에 속하며, 방 생성과 두 참여자 등록은 같은 트랜잭션이다. 인증·DB 연결·실시간 전파는 common에 둔다. 여러 서비스와 공통 계약 변경을 포함하므로 `feat/core/chat-messaging → dev/core` 경로로 리뷰한다.

## 검증 기준

1. 실행 가능한 Chat workspace, 명시적 추가 migration, 로컬 실행 문서.
2. 실제 PostgreSQL에서 두 참여자 전송·조회·읽음, 제3자 거절, 재전송 중복 방지, 동시 전송 순서, cursor/읽음 경계를 검증한다.
3. Kafka 이벤트 중복은 동일 방을 반환하고 실패는 재시도 대상으로 남는다.
4. Gateway에서 위조 헤더를 전달하지 않고 대상 Chat 인증 정보만 전달한다.
5. UI API 연결/메시지 병합/재시도 정책 테스트와 관련 서비스 빌드·기존 모바일 테스트를 실행한다.

원격 push/PR 병합/배포는 이 작업에서 실행하지 않는다. 현재 이미지 파이프라인의 다중 서비스 변경은 core 경로로 검증하며 신규 Chat 서비스의 개발 배포 등록은 별도 인프라 작업이다.

실행 설정과 테스트 방법은 [Chat README](../../packages/chat/README.md)를 따른다.

- Node 24.13.1 / pnpm 10.34.5의 frozen lockfile 설치와 전체 workspace 빌드 성공.
- `pnpm test:workspaces` 성공: Chat 20개(실제 PostgreSQL·Kafka·Gateway WebSocket 통합 16개와 Match GraphQL 어댑터 4개), Gateway 67개, Account 106개, Match 79개 및 공통 패키지 테스트 통과. Match 기존 DB 전용 테스트 4개는 해당 테스트 DB 설정이 없어 건너뜀.
- `pnpm test:ui` 20개와 `node --test scripts/*.test.mjs` 78개 통과.
- `pnpm --filter chat deploy --legacy --prod`로 만든 독립 패키지의 실제 서버 부팅·federation 스키마·health 경로, compiled migration 재실행 검증 성공.
- Docker 이미지 빌드와 실제 브라우저 조작을 통한 두 사용자 대화 검증은 실행하지 않음. 원격 push/배포 및 Auth/K3s 변경 없음.
